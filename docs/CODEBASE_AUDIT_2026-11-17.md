## 0. 结论、范围与证据口径

项目已具备一套适合轻量桌面音乐播放器的完整主干：多平台目录、两类取流渠道、本地资料库、独立播放队列、有界流式解码、桌面媒体控制、下载与备份，以及多种安装包和签名软件源。当前最值得投入的是**下载文件完整性、凭据传输和输入边界**，随后是异常恢复与性能可观测性。没有证据支持为了“架构现代化”引入大型 UI 框架、数据库或通用插件平台。

## 1. 项目整体架构分析

### 1.1 定位与技术特点

当前产品定位是 Windows / Linux 上的轻量原生音乐播放器：aino 自绘界面、C++17 业务、miniaudio 音频输出、精简 FFmpeg 子进程解码，QuickJS-NG 承载平台目录和部分 LX 音源协议。Windows 桌面媒体编译单元使用 C++20 / C++/WinRT；Linux 界面使用 X11 / XWayland，系统网络和桌面库由发行版提供。没有 Qt / GTK 的完整界面运行时依赖，但 Linux 图片解码会动态使用 GdkPixbuf，不能表述为“完全不使用任何相关组件”。

依据：[CMakeLists.txt](../CMakeLists.txt)、[入口](../src/main.cpp#L1)、[音频实现](../src/audio.cpp#L698)、[图片解码](../src/cover_decode.cpp#L18)、[构建边界说明](BUILDING.md)。

### 1.3 主要优势

1. **界面与后台已有明确交接机制。** ViewModel、版本化快照、post_ui 和 generation 共同减少后台结果直接改 UI、旧请求覆盖新请求的问题。播放队列、搜索结果和歌单详情是不同数据集。
2. **播放路径有资源上界。** Stream PCM 环形缓冲为 3 秒；含待回收管线在内最多 4 条流。旧流通过专用回收线程析构，避免 UI 直接 join 网络/解码线程。
3. **并发预算已落地。** 普通任务池 3 个普通工作线程，加 1 个交互保留线程，排队总量限制 256；封面最多 2 个 worker、32 个排队请求；下载并行度和队列也有限制。
4. **脚本并发不是“全局一把锁”。** Provider 每个运行时单独串行，集合锁只交换或取得 shared_ptr；搜索/取流可以使低优先级目录请求让位。LX 的 JS 回调仍在所属运行时执行。
5. **资料库有可用的轻量持久化设计。** SharedTracks 写时复制、FavoriteIndex、保存成功后发布版本、临时文件替换、自动轮换备份，均比立即改成数据库更符合当前规模。
6. **发行安全已有基础。** FFmpeg 源码固定摘要；更新安装包检查仓库/标签 URL、大小和 SHA-256；软件源脚本校验资产摘要和包身份，签名软件源发布还核对密钥指纹。
7. **历史问题有实际整改。** 不重复登记已经处理的“后台异常无边界”“普通启动无单实例锁”“队列每次变化都同步编码写盘”“收藏每帧全量两两比较”等旧结论。

依据：[快照与 UI 邮箱](../src/business.hpp#L848)、[后台任务池](../src/background.hpp#L96)、[流回收](../src/audio.cpp#L568)、[资料库容器](../src/library.hpp#L62)、[队列保存](../src/business.hpp#L3173)、[发布资产校验](../tools/build_apt_repository.py#L44)。

### 1.4 实际架构债务

- **业务全局状态很多，线程归属分散。** business.hpp 同时管理播放、账号、下载、备份、更新和视图状态。当前通过不同 mutex、generation、版本号约束，维护者必须同时理解多个不变量。适合先补“状态拥有者 / 可写线程 / 取消条件 / 发布位置”表，再在原文件内按职责组织小型状态对象。
- **模型与平台协议耦合较深。** library.hpp 需要 Track，却通过 sources.hpp 连带依赖 Provider、LX、QuickJS；login.cpp 也通过账号 API 进入这条依赖链。优先减少实现层反向引用和无必要 include，不直接改变既定文件结构。
- **本地音频标签手术没有共享的容器验证边界。** 下载、嗅探、标签修改和最终成功状态分在不同函数；“网络下载成功”与“标签改写后仍完整”缺少明确区分，产生本报告最严重的数据完整性问题。
- **宿主复用依赖 lx::detail。** 平台目录与第三方脚本的权限和生命周期不同，却共用内部实现命名空间。可以在原模块内定义窄的宿主适配函数，保留已有外部 API，逐步减少对第三方协议内部细节的依赖。

### 2.1 API 与接口设计

已有的 audio::Player::take_transition、Stream::cancel、wait_for_stream_cleanup 等接口说明了关键生命周期，方向正确。建议在不改现有签名的前提下补充：

- Player 的控制操作由哪个线程调用；哪些查询可跨线程；error() 返回引用的有效期；Stream 取消后不可复用，以及清理等待的先后条件。
- music::Track::current() 当前只限制 chosen 上界，负数会转成巨大 size_t。已追踪的 UI 换源函数和 decode_track 做了下界校验，**尚未证实生产路径可传入负值**；作为接口防御建议加入下界处理或 debug 断言。
- ResolveResult::ok 表示拿到候选，还是已经通过消费者加载，应明确；现有 ResolveAccept 已能区分这两个阶段，适合保留。
- Provider::call 对 search/board 会推进 Promise；resolve/request 则直接处理返回值，async request 可能被 JSON.stringify 成空对象。当前捆绑目录方法使用同步 HTTP，文档也如此约定，不能把“没有全面异步支持”误报为所有平台现已失效。可选方案是明确只支持同步，或在同一个受预算约束的 settle 边界支持 Promise。
- HTTP 成功内容统一走 Response::ok()；保留可选诊断 body 时也要与可消费结果分离。[封面](../src/cover.hpp#L223)和[下载封面](../src/business.hpp#L2159)只检查 status，Linux 网络中途失败时可能把部分响应继续送解码器。
- bool + error 字符串可以继续对外保留；内部逐步增加 Cancelled、Timeout、Unauthorized、InvalidData、Unsupported、IOError 等错误类别，UI 文案与调度策略分开，避免依赖字符串猜错误。

依据：[Player API](../src/audio.hpp#L75)、[Track::current](../src/sources.hpp#L150)、[换源入口](../src/business.hpp#L4920)、[Provider 返回处理](../src/provider.hpp#L450)、[平台 HTTP 实现](../src/net_curl.hpp#L135)。

### 2.2 测试体系评价

项目已经有实质测试，不应评价为“没有单测”：

- player_tests.cpp：协议/目录解析、脚本宿主、取流路由、库与队列数据、标签读取、格式准备等。
- controller_tests.cpp：无窗口业务状态、队列顺序与连续播放、下载状态、资料恢复、歌词翻译、封面及缓存边界等。
- interaction_tests.cpp：输入捕获、弹层/拖动生命周期，以及 Linux DPI / 字体相关路径。
- Python 驱动：本地 HTTP 登录边界、真实隔离浏览器回传、格式解码、封面并发、软件源元数据。
- memory_probe/profile_memory 及历史文档提供专项观测工具，不能代替持续泄漏、音质或性能基准。

确定缺口：

1. tests 下未找到对 tag::embed_mp3、embed_m4a、inject_mp4_tags 的写入调用；已有标签测试主要覆盖读取。tools/probe_tag.cpp 的联网手工探针不等于离线容器写入验收。
2. 缺少针对本文畸形 JSON 数值、超长 LRC 时间戳、MP4 size/count/depth、磁盘延迟写失败、封面 worker 抛异常的专门覆盖。
3. 测试依赖发现会改变 CTest 注册集合，发布验收没有统一核对“该平台预期项目是否都注册”。Arch 当前以构建、安装、版本/解码器信息和 Xvfb 启动为主，并没有同样运行 CTest。
4. 没有生成覆盖率数据，不能给出可靠覆盖百分比；也没有本次长时间播放、内存泄漏或竞争检测结论。
5. 建议把可重复的离线样本和故障注入纳入**下一次获准发布时**的验证。日常只做必要编译、静态分析和代码审查；不建议新增自动夜间回归或通过 push 绕过项目规则。

### 2.3 构建、跨平台与文档

- CMake 默认 AINO_BUILD_TESTS=OFF 与用户规则一致；PCH 只含 aino 声明，业务单元跳过，避免重复实现。
- Windows 播放器要求 MSVC，不应把 FFmpeg helper 的 GCC 构建误写成播放器仍支持 MinGW。Linux 使用发行版依赖，当前没有 macOS 播放器交付；aino 内有 macOS 后端不代表整套业务已支持 macOS。
- FFmpeg 源码哈希、精简编译选项、嵌入前版本/许可/体积检查值得保留。这里没有独立法律合规结论，也没有断言所用上游版本没有已知漏洞。
- Windows 安装器按每用户权限运行；更新 SHA-256 保证下载资产与预期摘要一致，但不能替代独立代码签名或被攻陷发行账户之外的信任锚。
- APT/RPM/Arch 发布工具有相似的资产下载、大小/摘要/身份检查；不同包管理器的签名、元数据与校验流程不可简单合成一个“大一统脚本”。
- ADR、旧 PROJECT_REVIEW、内存文档是带日期的演进记录，应保留；新维护者还需要一份简短的当前状态索引，避免把旧版 MinGW、旧音频缓存设计等当作现行规范。

### H-01：搜索明文携带账号 Cookie

**定位**：[providers/netease.js:15](../providers/netease.js#L15)、[search:54](../providers/netease.js#L54)；[宿主传递请求头](../src/lxsource.hpp#L505)。

search 构造 http://music.163.com/...，并把 cookieHeader() 的结果放入 Cookie；该函数会拼入 ctx.cookie('netease') 的账号登录态。HTTP 桥接没有在此处移除 Cookie。因此在持有登录 Cookie 并搜索时，首次外发请求即可经过未加密连接。之后是否重定向为 HTTPS 不能消除首次传输的暴露。

**影响**：网络路径上的监听者可看到请求内容与登录凭据；未登录仍暴露搜索词。不是说已经发生过凭据窃取。

**最小修复方案**：将此入口改为 HTTPS，并在宿主层为携带 Cookie/Authorization 的远端请求拒绝 HTTP 与 HTTPS→HTTP 降级；不禁止无凭据的兼容音频流和应用本机 loopback HTTP。若平台 HTTPS 不可用，应明确失败或采用经过确认的无凭据查询方案，不自动退回携带 Cookie 的明文请求。

**验收条件**：静态检查 URL/请求头；下次获准发布时用隔离假 Cookie 检查首跳和重定向，不使用真实账号凭据。

### H-02：MP4 chunk offset 被错误平移

**定位**：[tag::shift_chunk_offsets:501](../src/tag.hpp#L501)、[inject_mp4_tags:539](../src/tag.hpp#L539)、[verify_mp4:614](../src/tag.hpp#L614)；生产调用：[start_download 标签阶段](../src/business.hpp#L2149)。

所有插入分支均按新增字节数调整 stco/co64，却没有检查被引用媒体数据是否真的移动。第一分支的 moov_end <= file.size() 在插入之后始终满足。

对于 ftyp → mdat → moov 的常见布局，修改尾部 moov 并不移动前方 mdat，原音频偏移应保持不变；当前却统一加上 grew，导致解码指向错误位置。verify_mp4 只检查顶层 atom 长度首尾相接，所以仍可能返回成功并写回。

**影响**：开启内嵌并实际取得封面/歌词时，下载本来成功的 M4A 可能在标签步骤被破坏；快进、解码或播放可失败。moov 在前的文件也需要按插入点、实际引用和边界处理，不能简单交换一个条件覆盖全部布局。

**方案**：先解析容器布局，按插入位置只调整引用到被移动区域的 offset，检查加法溢出和 stco→co64 需求；不支持的布局保持原文件。完成深层结构和样本偏移验证后才替换。保持 tag::embed 外部签名与现有下载行为，内部增加容器计划/验证步骤。

**验收条件**：moov 前/后、多个 mdat、stco/co64、已有与缺失 meta 的离线样本；验证媒体 payload 不变、音轨可完整解码和 seek。仅顶层 atom 校验不够。

### H-03：其他容器被当成 MP3 加上 ID3

**定位**：[tag::embed:650](../src/tag.hpp#L650)、[容器嗅探](../src/business.hpp#L1373)、[生产调用](../src/business.hpp#L2171)。

embed 只识别 ftyp（交给 MP4）与 fLaC（明确不支持），其余全部 embed_mp3。现有下载/解码路径能处理 Ogg、Opus、WebM、WAV、AAC 等，因此此处不是只会接到 MP3。给 Ogg/WebM/WAV 直接前置 MP3 ID3 标签不是对应容器的正确写法；部分解码器可能容忍，但不能依赖容错维持兼容。

**影响**：文件头、扩展名和实际容器不再一致，可能无法播放或被其他播放器拒绝；不是所有 AAC 文件前置 ID3 都必然不可播放。

**方案**：集中复用内容识别，明确白名单，仅已实现且验证过的容器进入写入器。未知/不支持格式返回 Unsupported，原音频保持字节不变，可提示或写同目录 sidecar。不要仅根据扩展名决定。

**验收条件**：为每个当前支持的下载容器检查“支持则正确写入；不支持则原文件哈希不变”。

### H-04：畸形 MP4 可以卡死标签 worker

**定位**：[tag::find_atom:446](../src/tag.hpp#L446)、[shift_chunk_offsets:501](../src/tag.hpp#L501)、[退出等待](../src/business.hpp#L5862)。

find_atom 跳过不匹配的 size=1 atom 时，直接把 64 位扩展长度加到 p，没有检查最小头长、剩余字节或 p 是否前进。扩展长度为 0 时 p 不变，while 永不结束；畸形长度还涉及加法溢出。此函数不检查取消信号，后台通用 catch 不能处理死循环，退出 join 也可能一直等待。

同一写入器还存在相邻边界缺口：递归容器下降没有深度上限；stco/co64 的 count 只按整个 file.size() 截断，没有约束在当前 atom 的有效表项范围内。这些都应在一个容器边界修复中处理。

**影响**：恶意/损坏媒体可占用 CPU、阻塞下载 worker，并拖住退出。下载源能返回任意媒体是风险入口；本次没有制作或运行攻击文件，也不声称已证明代码执行漏洞。

**方案**：统一安全 atom reader：head ≤ size ≤ remaining；用 remaining 比较避免加法溢出；每轮 p 严格增加；限定嵌套深度、条目数量和实际盒边界；长循环响应取消。失败时不得改原文件。

### M-01：新建 MP4 元数据结构错误

**定位**：[kIlstHdlr 与新建分支](../src/tag.hpp#L531)。

meta_body += "\x00\x00\x00\x00" 使用以 NUL 开头的 C 字符串重载，实际追加 0 字节；随后直接 append(kIlstHdlr, 25)，但这 25 字节是 hdlr 的 payload，没有 atom("hdlr", ...) 包装。结果不是预期的“meta FullBox 四字节 + hdlr 子盒 + ilst 子盒”。注意 payload 自身以零开头，不能把结果简单描述为“文件中完全没有前导零”；错误在于层级和字段边界。

**影响**：原文件没有 udta/meta 时，新封面/歌词可能被标准读取器忽略；顶层 verifier 检不出内层结构错误。

**方案**：显式追加定长零字节、构造完整 hdlr 子盒，深层验证 meta/ilst；已有 covr/歌词应明确替换策略，避免反复追加重复条目。

**验收**：无 udta、仅 udta、已有 meta/ilst 四条分支分别检查，多次写入应幂等且保留无关元数据。

### M-02：MP3 丢失已有 ID3v2 信息

**定位**：[tag::embed_mp3:383](../src/tag.hpp#L383)。

实现跳过整块旧 ID3v2，只重建 APIC 和 USLT。原有标题、歌手、专辑、序号、用户文本、响度标签等均可能丢失。开关名是“内嵌封面/歌词”，并未授权清除其他标签。

**方案**：保留非目标 frame，只替换被请求的 APIC/USLT；遇到不支持的版本、压缩、unsynchronisation 等明确保留文件并提示，不做有损“兼容改写”。

**影响/验收**：对下载自带元数据的 MP3 影响明确；保留帧内容、音频 payload 和只更新一个字段的用例应加入下一次发布验证。

### M-03：fclose 失败仍替换原文件

**定位**：[tag::write_replace:90](../src/tag.hpp#L90)。

只检查 fwrite 字节数，忽略 fclose 返回。stdio 的缓冲数据可在关闭时才报告磁盘已满或 IO 错误；当前仍会把 .tagtmp 替换为正式文件并报告成功。

**方案**：独立记录 write/ferror/close 结果，任何失败均删除临时文件并保留原文件；与 Library::save 和 queue_save 已有写法一致。此修复与断电持久性 R-04 不同，不能互相替代。

**验收**：故障注入延迟写失败、短写、替换失败；不要用在真实音乐上填满磁盘来验证。

### M-04：JSON“严格解析”会接受无效输入

**定位**：[Parser::parse_number:186](../src/json.hpp#L186)、[parse_string:143](../src/json.hpp#L143)、[js::parse:296](../src/json.hpp#L296)。

parse 不要求去掉尾部空白后 p==end；parse_number 扫描过宽，stod 又不检查 consumed length。因此有效对象后面有垃圾仍可成功，数组中的 1.2.3 也会按 1.2 消费。默认模式还接受单引号、None、未知转义和原始控制字符，lenient 与 strict 的界线不完整。

**影响**：资料库/队列/备份的“损坏则保留”判断可能误接受坏数据，后续正常保存可丢弃未解析尾部；不能据此断言任意损坏文件都会被接受。

**方案**：新增真正的 strict whole-document 解析供持久化使用；保留平台响应确需的显式 lenient 路径，避免一次收紧破坏既有兼容。数字语法、转义、尾随内容分别校验。

### M-05：JSON 数字转整数存在未定义行为

**定位**：[Value::num/integer:57](../src/json.hpp#L57)、[decode_track](../src/library.hpp#L150)、[目录数据转换](../src/sources.hpp#L1614)。

integer 对 double 四舍五入后直接转 long long，没有检查 isfinite 或可表示范围。字符串 num 允许 stod("nan")、stod("inf")；合法 JSON 中的 1e100 也可超过 long long。转换到整数之前已经越界，调用者之后再 clamp 无法修复。

**影响**：导入数据、持久化和平台响应可把异常数值带入业务，表现依赖编译器；不能把它描述成已经稳定复现的崩溃。

**方案**：集中实现有类型范围的 checked conversion，先检查有限性、输入语义和舍入后边界，再转换；明确非法值返回 fallback 还是报错。进一步检查 long long→int 以及秒→毫秒乘法，不能只修第一层转换。

### M-06：LRC 时间戳的算术边界与格式不一致

**定位**：[lyr::parse_stamp:41](../src/lyrics.hpp#L41)。

每位数字执行 long long 累乘累加，小数位数又用 int scale 反复乘 10，最后还执行 mm*60000 等运算；均未设位数/范围或溢出检查。超长时间标签可造成有符号溢出。注释声明支持 mm:ss:xx，但小数缩放只在发现点号时进行，例如同样两位小数的冒号格式与点号格式不会得到相同毫秒结果。

**影响**：远端或本地畸形歌词可触发未定义行为；部分歌词同步时间错误。

**方案**：按明确语法解析，限制分钟/秒/小数位，进行 checked arithmetic；统一两个小数分隔符的既定兼容行为。超出支持范围的单行应安全拒绝，其他正常歌词保留。不要通过任意截断整份歌词掩盖错误。

### M-07：离线文件与实际平台来源不一致

**定位**：[downloaded_path:1145](../src/business.hpp#L1145)、[下载登记:2175](../src/business.hpp#L2175)、[重新定位登记:4144](../src/business.hpp#L4144)、[优先本地播放](../src/business.hpp#L1587)。

一份按当前选定 variant 下载的文件被登记给 track.variants 的全部成员。查找又遍历全部变体而非 track.chosen，随后播放显示仍可能采用当前选中的平台信息。因此用户切到 QQ 版本，实际可能复用另一平台文件，却没有准确展示真实来源；预加载也使用该查找。

**影响**：平台、版本和音质来源不能可信追溯，且与 providers/README 中“当前选定平台、不静默遍历其他变体”的契约存在冲突。跨变体离线复用本身可以是产品策略，但必须明确授权和标识，不能把聚合“同一首”当作文件身份完全相同。

**方案**：保存实际 variant_uid、容器、质量与下载来源；默认精确匹配选择。显式允许跨变体复用时，UI 显示实际来源。兼容旧下载记录，用“历史来源待确认”迁移，不能凭旧映射猜真实平台。

### M-08：封面异常导致队列永久失活

**定位**：[Store::get/drain:158](../src/cover.hpp#L158)、[load:193](../src/cover.hpp#L193)、[通用异常边界](../src/background.hpp#L78)。

get 先置 entry.state=1、递增 workers_，再启动后台 service；drain 只在正常遇到空队列时递减 workers_。线程创建/排队失败，或 load 中的分配、容器、路径转换等抛异常时，外层会报告异常，但封面内部 worker 计数与下载中状态不会回收。两次此类失败可耗尽逻辑上的两个 worker，后续请求一直排队。

**方案**：提交失败回滚；worker 退出用 RAII 回收计数；逐项捕获并把同一 generation 的 entry 转为失败/可重试，通知 UI。WIC/GObject 清理也改为局部 RAII，避免分配异常跳过 release/unref。

**验收**：注入提交异常、单项解码异常、清缓存与异常交错；确认后续正常 URL 仍可完成。此项不是“通用后台线程没有 catch”，后者当前已有保护。

### M-09：配置音量在启动时直接越界转换

**定位**：[config::load:616](../src/business.hpp#L616)、[initialize:5338](../src/business.hpp#L5338)、[配置保存:729](../src/business.hpp#L729)。

音量通过 atof 直接存入 float，启动随即 int(g_ui.volume)，保存也做相同转换。volume=nan、inf 或巨大有限值可到达未定义的浮点→整数转换；正常 set_volume 的夹限不能保护这条启动路径。quality 也直接 atoi，虽然多数消费处有默认分支，仍应按 0～2 规范化。

**方案**：读取时就检查完整数值、有限性和范围，使用默认值/规范化结果并标记脏配置；不要等音频设备层夹限。

**验收**：损坏配置不会导致启动异常或极端音量；保持旧版合法整数配置兼容。

### M-10：高风险路径没有对应的发布验收清单

**定位**：[测试注册](../CMakeLists.txt#L211)、[标签探针](../tools/probe_tag.cpp)、[发布矩阵](../.github/workflows/release.yml)。

标签读取和音频解码测试不能覆盖“写标签后破坏原文件”；缺少浏览器/Python/Xvfb 时部分测试不注册，而 --no-tests=error 只防止整个集合为空。不能把不同平台的 CTest success 理解为覆盖项目完全一致。

**方案**：在下次发布流程中输出并校验每个平台的预期测试清单；必须项依赖缺失明确失败，允许省略项明确记录原因；补齐 H/M 对应的离线失败样本。Arch 可保留安装兼容验证为主要责任，但应明确共享核心行为由哪些平台承担，避免虚称每个平台做了全套验证。

**边界**：这是补齐发布门槛的建议，不是要求在本次审查或日常提交执行回归。

### Low 级问题

**L-01：同平台合并与注释不一致。** [merge_into:830](../src/sources.hpp#L830) 找到同平台已有变体后，低码率直接 return；遇到不同 ID 的更高码率则离开循环并 push_back，旧项仍在。同平台药丸可能重复，与“同源只留一条”注释不符。先确认产品策略：要替换应就地更新，要保留不同发行版本应使用不同轨道/明确版本标识；不要只为去重删掉合法版本。

**L-02：自有代码的警告门槛不显式。** [CMake 目标选项](../CMakeLists.txt#L159) 配置了编码、异常和体积选项，但没有给自有目标统一设置 /W4 或 -Wall/-Wextra，也没有受控的静态分析入口。建议只对自有范围逐步启用，先修新增警告，不对 vendor 或 aino 上游头一刀切 Werror，更不运行全仓格式化。

**L-03：发布文档落后于工作流。** [BUILDING 发布流程](BUILDING.md#L53) 仍描述 Windows/Ubuntu 两端成功后发布 exe/deb；[release.yml](../.github/workflows/release.yml#L197) 实际依赖 windows/linux/rpm/arch 四项并发布四类平台包。应把当前规范与历史举例分开，补 Fedora/Arch 职责、包签名索引与人工发布触发边界。历史版本号示例不必抹去，也不应把旧 ADR 的验证结果改写成新结果。

### 4.2 CPU、GPU、内存与 IO 的评估边界

- **CPU**：最确定的异常热点是 H-04 的无限循环；正常热点候选是软件渲染、EQ、元数据编码和大量脚本初始化。没有采样数据，不能排名正常运行时谁最高。
- **GPU**：没有从当前播放器路径发现自有 GPU 资源队列或着色器系统，不能臆造显存泄漏或 GPU 锁竞争。系统合成器仍可能用 GPU；需按进程区分。
- **内存**：单条 Stream PCM 分配 48000×3×2×2 = 576000 字节，约 0.55 MiB；4 条流的这部分合计约 2.20 MiB。**这不是总播放内存**，未包含 FFmpeg、miniaudio、网络块、字体、图片和运行时。
- **封面**：12 MiB 是 Store 内持有图像的像素预算，不是全进程图像内存硬上限；外部 shared_ptr、解码临时数据仍可存活。Linux 正常路径有原生降采样，fallback 仍可能先解完整图像。
- **磁盘**：无法流式解码时可回退完整文件及 PCM WAV；临时磁盘量与时长/声道/采样率相关。不要把所有 fallback 文件都按固定 48 kHz 双声道估算，因为 prepare_file 没强制该输出采样率/声道数。
- **锁竞争**：队列编码已在播放锁外；脚本在同一 runtime 内序列化是正确性约束。后续应记录等待时间和持锁范围，优先修 UI 同步 join，而不是加更多线程或取消 runtime 锁。
- **泄漏**：COW 快照、历史记录、脚本对象和分配器保留页可能看起来像持续占用。只有固定工作负载多轮后 live 对象/句柄持续增长，才能进一步判断泄漏；历史 Working Set 差值不能直接当泄漏证据。

历史 [Linux-memory-profile.md](Linux-memory-profile.md) 已区分私有驻留、私有提交、Working Set，并记录脚本影响。那些值对应旧提交、短测和特定机器，本报告不把它们当 HEAD 的测量结果，也不相加不同基线的收益。

### 7.2 大改动应先评审的内容

以下事项本次仅给方案，未执行：

- **流式标签改写**：需要明确允许的容器结构、临时空间、64 位偏移、失败原子性与取消语义；不应在未验证的情况下直接替换全部写入器。
- **总脚本预算/懒加载策略**：须先说明令牌初始化是否会过期、冷启动代价、当前与下一曲谁优先，以及初始化网络流量；已有 collect_idle 不能重复发明成“从零实现卸载”。
- **输出格式/独占设备**：影响解码格式、重采样、EQ、音量、设备重建和 gapless；必须保持默认共享模式，并承认独占可能影响其他应用发声。
- **数据格式升级**：需要旧格式可读、未知字段策略、可回滚/保留旧文件；不能把所有旧下载记录标为真实已验证。
- **原生 Wayland/可访问性**：须单独说明窗口、剪贴板、快捷键、屏幕坐标、文本输入和桌面权限边界。IME 仍以用户确认的版本为参照，未实机确认的新修复不提交、不推送、不发布。

不推荐当前立即做的“大重构”：替换 aino 为 Qt/GTK、为 JSON 立刻引入数据库、把每个函数拆成独立源文件、引入通用 DI/插件框架、把全部同步平台接口同时改 Promise、全仓格式化。这些都没有与当前风险相称的证据收益。

### 9.2 短、中、长期建议

下表优先级面向本项目。P0 是当前可靠性基础；P1 是修复后最有价值的增量；P2 应由需求与测量证明。所有“收益”是目标，不是已实现效果。

| 方向 / 时段 / 优先级 | 推荐理由与解决的问题 | 实现思路 | 难度、预期收益与代价 |
| --- | --- | --- | --- |
| I-01 可信离线资产与来源卡片；短期 P0/P1 | 多平台聚合的价值依赖“实际播放了哪一份”。直接解决 M-07，提升下载/离线可信度 | 记录真实平台 variant、容器、标称/探测质量、下载时间、文件大小与按需内容摘要；详情页展示精确/跨变体/历史未知匹配；旧记录渐进迁移 | 中；减少串版、误报音质和重复下载。按需计算摘要会产生 IO，不能每帧哈希或自动替换用户文件 |
| I-02 音源能力与脱敏诊断；短期至中期 P1 | 当前“兼容部分 LX”和第三方平台接口最难排障；用户不应靠脚本初始化成功猜能否播放 | Provider/LX 显示能力表、协议版本、脚本指纹、当前平台/音质、失败类别、预算与首段状态；导出诊断先脱敏；脱敏 fixture 与能力契约绑定 | 中；提高报障与兼容迭代效率。日志有隐私成本，必须避免 Cookie、认证 URL 和原始浏览器 profile；不承诺补完整 Node API。[R3] |

| I-08 可选音频指纹辅助本地资料修复；长期、低优先 P2 | 只在本地文件元数据缺失且用户确有需求时有意义；多平台“同名即同曲”不可靠 | 优先做本地信息完整性检查；之后评估按用户选择生成音频指纹、查询可信元数据候选，预览标题/版本/专辑再写 sidecar；不修改账号曲目 ID | 高；可提高旧曲库元数据质量。涉及网络隐私、服务限制、不同发行版识别与额外依赖；没有用户需求前不实现。参考 [R1] 所列指纹补标签能力 |

### 9.3 发展方向的取舍标准

建议持续强化三个可以验证的产品价值：**轻量且可预测的资源使用、可解释的多源播放、可靠的本地/离线资料**。新增能力应复用现有快照、任务预算、平台身份和用户数据保护机制，并回答以下问题：

1. 是否解决当前用户可描述的问题，能否从现有数据与模块增量实现？
2. 是否会改变真实音频来源、音乐文件内容、账号权限或输入行为？如会，是否有显式选择、迁移和撤销路径？
3. 能否在默认关闭或不使用时几乎不增加启动/常驻成本？
4. 是否能定义清晰的故障行为、兼容范围和下次发布时的验收条件？

目前不建议优先堆叠云同步、社交、通用脚本市场、自动跨平台换歌、大而全的音频工作站功能。这些会扩张账号、安全、版权/服务依赖和维护面，而本次已确认的文件完整性与凭据问题尚未解决。
