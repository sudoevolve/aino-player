# Aino Player 项目审查与优化建议

审查日期：2026-11-14。代码基线：`de788c5`，前置本地播放提交为 `46df967`。

本报告覆盖架构、代码格式、性能、冗余清理和功能完整性。结论来自代码路径与差异审查；本轮 Windows Release 主程序已编译通过，未运行回归、在线音源测试、CI 或 Linux 编译。下述风险未全部实机复现，性能收益须后续测量，不能据此声称 Linux 内存或歌词 CPU 已降低。

## 1. 总体判断

项目已有合理的模块方向，但业务状态、异步任务和持久化的约束还不够集中。主要问题不是缺少模块数量，而是几个大文件内职责交错、状态生命周期依靠约定，部分操作成本随歌单规模增长。

建议保持现有业务、UI、main 入口以及音频、桌面适配等边界，在文件内部整理状态和职责，不继续拆成大量小文件。

| 优先级 | 问题 | 影响 | 建议下一步 |
| --- | --- | --- | --- |
| P1 | 后台任务无统一异常边界，启动失败缺少退出清理 | 异常或初始化失败可能触发进程终止 | 任务异常上报、完成标志保护、RAII 退出清理 |
| P1 | 队列保存持播放锁序列化，延迟保存每次新建线程 | 大队列交互卡顿、连续操作线程膨胀 | 锁内取快照，锁外编码，单写入任务合并 |
| P1 | 多实例可能同时写配置、队列和资料库 | 覆盖更新、临时文件冲突 | 单个可写实例与启动锁，其他启动统一转交 |
| P2 | 歌词每帧仍遍历所有排版行 | 长歌词、译文歌词额外消耗 CPU | 可见区二分定位、缓存原文行映射 |
| P2 | 收藏查询线性，批量收藏重复扫描 | 大收藏列表绘制和批量操作变慢 | 随资料库版本更新的歌曲身份索引 |
| P2 | 部分平台歌单只加载第一页、最多 200 首 | 播放与保存得到不完整曲目快照 | 歌单曲目分页契约、完整性提示 |
| P3 | 格式缺少约定、注释失真、闲置成员 | 修改成本升高，文档误导 | 小范围清理，格式变更独立提交 |

P1 表示优先解决的稳定性和数据风险，不表示已发生用户数据损坏；P2 为明确性能路径或功能缺口；P3 为维护性改进。

## 2. 项目架构

### 现有边界

| 文件 / 模块 | 当前职责 | 评价 |
| --- | --- | --- |
| `src/main.cpp` | 生命周期、窗口、桌面接入、启动参数 | 入口约 303 行，主体较清楚，但错误退出清理不统一 |
| `src/business.hpp` | 播放控制、快照、搜索、歌单、设置、下载及任务协调 | 约 4361 行，状态与业务种类过多，需内部组织 |
| `src/ui.hpp` | 页面、列表、弹出菜单、底栏、歌词及交互 | 约 2513 行，已有 ViewModel，局部仍可直接改设置状态 |
| `src/sources.hpp` | 平台歌曲类型转换、播放解析、目录和歌词协调 | 约 1805 行，平台特例密集 |
| `src/provider.hpp`、`providers/*.js` | JS 平台搜索、发现、歌词和目录协议 | 搜索已经统一到 JS，不应再维护第二套 C++ 搜索 |
| `src/lxsource.hpp` | 第三方脚本宿主、检测、取流、健康及测速 | 约 1780 行；运行时与调度同文件，需明确内部层次 |
| `src/audio.cpp`、`src/desktop.cpp`、`src/login.cpp` | 音频、系统集成、浏览器登录 | 独立编译，边界基本合理 |

`src/aino.hpp` 是上游框架，不计入播放器自身业务文件膨胀，也不应因播放器局部问题随意修改。

### 应保留的设计

- UI 通过业务动作和 ViewModel 读取状态；播放快照按版本更新大列表，已经避免每帧无条件复制。
- 资料库已有单后台写入任务、80 ms 合并窗口、不可变发布及保存失败保护，不再是收藏时 UI 线程同步写整库。
- Provider 集合锁只用于取得运行时引用，各平台独立执行锁，网络期间不再持有全局集合锁。凭据采用调用线程的快照。
- 请求代次和取消机制已覆盖多处搜索、详情、歌词和取流；应统一这些机制，避免另起一套平行实现。

### 架构风险与改进

**A1：任务异常与退出清理。** `src/background.hpp:26` 的线程直接调用 action，没有最外层异常处理；未被任务内部捕获的异常会调用 `std::terminate`。`src/main.cpp:157` 启动后台平台加载后，初始化或建窗失败直接返回，可能留下可连接线程进入静态析构。建议在现有后台模块内统一完成标志、异常发布和退出排空，并给 main 增加覆盖所有返回路径的 RAII 清理。不要只加空 catch 隐藏错误。

**A2：多实例写入。** `src/main.cpp:151` 仅文件打开启动尝试转交，普通启动仍可能产生多个写入实例。`src/library.hpp:248`、`src/business.hpp:2457` 使用固定 `.tmp`，进程内 mutex 无法保护另一个进程的写入。建议按用户加启动锁，普通启动和文件打开均转交已有实例。仅更换唯一临时文件名不能解决资料库最后写入者覆盖前者的问题。

**A3：状态所有权。** `UiState`、全局业务状态、多个 generation、锁和任务队列集中于 business。建议在原文件内按播放、目录、资料库、下载、设置组织状态结构，每个结构注明 UI 线程专有或受哪把锁保护；UI 修改业务状态统一走动作。无需引入复杂继承体系或新依赖。

**A4：同平台请求仍串行。** `src/provider.hpp:129` 的运行时锁包含同步 JS HTTP，虽已解决全局锁，慢歌单请求仍可能阻挡同平台搜索。可先让显式点播 / 搜索优先，淘汰过期后台任务，再根据实际等待时间决定是否需要只读独立运行时；不宜直接无限复制 QuickJS 实例。

## 3. 代码格式和可维护性

仓库未发现 `.clang-format`、`.clang-tidy`、`.editorconfig`。C++ 中长单行、多个语句挤在同一行，以及中英文历史注释混合，增加了锁范围、错误分支和取消检查的审查难度。

建议先增加符合现有风格的基础格式约定，仅用于新代码或修改范围。并发、网络和持久化代码优先展开成清晰的控制流。不要把整库自动格式化与功能修复混在一个提交，也不要自动重排上游 aino、miniaudio、QuickJS 等代码。

发现的具体清理点：

- `src/business.hpp:2977` 仍以“五、界面”标注资料库写入业务段，章节名称失真。
- `src/business.hpp:597` 附近帧率注释与当前歌词基础刷新频率不一致；实际还包含按需动画，不能简单描述为固定 60 FPS。
- `src/lxsource.hpp:102` 同一句回调说明重复两次。
- 平台名、质量档位、健康状态数字散落多处，适合在现有模块内统一有语义的常量或枚举；先从有修改需求的位置推进。

## 4. 性能与内存

### P1：队列落盘锁与线程数

`src/business.hpp:2436` 的 `queue_save()` 在持有 `g_mu` 时编码所有歌曲，虽然写盘在后台，UI 快照和播放状态更新仍可能等这把锁。`queue_mark_dirty()`（2474）每次修改都创建一个睡眠 1.2 秒的线程；现有 generation 只合并落盘次数，未合并线程数。

改进：锁内捕获带版本的不可变队列视图，锁外序列化；使用一个持久写入任务与可唤醒截止时间，退出时统一排空。评估指标为大队列下锁持有时长、UI 帧耗时和连续编辑后的线程峰值。

### P2：歌词只绘制可见行，但仍扫描全部行

`src/ui.hpp:2305` 每帧线性查原文行对应显示行，2345 起遍历整个排版列表后才裁掉不可见行。现有排版缓存和低频基础刷新已经有作用，剩余问题是遍历范围。

改进：排版时建立原文行到首个显示行的映射，利用已排序的行顶坐标二分可见范围，保留点击、滚动、译文、居中和渐隐外观。评估长歌词 / 双语歌词每帧耗时，不能以静态代码推算 CPU 降幅。

### P2：收藏身份查询和大资料库复制

`src/library.hpp:205` 的 contains 逐首扫描收藏；歌曲行与底栏多次调用，批量收藏（`src/business.hpp:3036`）又重复 contains / toggle 扫描。可随资料库版本建立歌曲身份索引，索引须保持现有跨来源 variant 匹配语义。

资料库写入虽已异步，每批仍在 `src/business.hpp:3008` 深拷贝整个 Library 并编码整份 JSON。打开本地歌单（3335）还复制整份曲目，详情历史最多保存八页完整数据（3315）。这些会造成大歌单下的额外分配与峰值，适合逐步共享不可变曲目集合，减少深拷贝。应先测量，再决定是否拆分最近播放等高频小数据的存储；现阶段无需换数据库。

### P2：JS / C++ 数据桥重复处理

`src/provider.hpp:74` 先把歌曲完整 JSON stringify / parse 到 metadata，再逐字段从 JS 读取；通用 request（414）也通过 JSON 转换。建议标准化有界字段对象，避免保留无用原始响应，并一次提取数据；必须保留酷狗质量 hash、咪咕 copyrightId、歌手和专辑 ID 等业务必需字段。

### 内存不能混淆的几件事

- `src/audio.cpp:326` 的 48 kHz、双声道 16-bit、三秒 PCM 环形缓冲约 **0.55 MiB**，它本身不能解释几十 MiB 的 Windows / Linux 差距。
- `src/cover.hpp:124` 已有 **12 MiB 解码像素预算**及闲置回收；这不等于整个封面模块的总内存，包括外部引用、解码临时数据等仍需分别统计。
- QuickJS 的 256 / 512 MiB 是**允许使用的上限**，不是每个运行时启动即占用这么多。六项并行脚本初始化可能增加峰值，但实际值需要采样。
- Linux RSS 与 Windows Private Bytes 口径不同；需比较相同状态下的私有 / 共享页、字体图标、图形缓冲、JS 堆、歌曲数据和线程，FFmpeg 子进程另列，不能把 RSS 差额直接称为泄漏。

### 编译速度与 EXE 体积

`src/main.cpp` 承担 AINO_IMPLEMENTATION 并包含业务、UI 和平台桥接的大量头文件；`CMakeLists.txt:109` 的主目标仅 main 和 cover_decode 两个编译单元。改 UI / business 容易重新编译重量级主单元，这是增量构建慢的明确结构因素。

先记录 main 编译与链接各自耗时，再考虑利用现有 cpp 文件或实现宏隔离稳定实现，保持用户要求的少文件布局。预编译头只能作为测量后的选项，不应默认增加构建复杂度。体积分析应比较相同编译参数下的 PE 节与内嵌 FFmpeg 资源，不能把新本机构建和上次 release 直接作功能增量对比。

## 6. 功能完善性

### 优先补齐

1. **完整歌单曲目分页。** `src/sources.hpp:1327` 的 board_tracks 固定请求 page 0；`src/business.hpp:3376` 和 3675 限制 200 首。影响酷我、酷狗、咪咕的打开和保存，不是已修复的网易云完整歌单路径，也不同于发现卡片“加载更多”。应返回曲目总量 / 下一页，逐页去重，支持取消、失败重试与部分内容提示，防止不完整结果覆盖已保存完整歌单。
2. **统一任务状态与错误详情。** 音源已有详细错误弹窗，但通用 toast（`src/ui.hpp:2170`）仍会截断长错误。建议短摘要加“详情 / 复制”，建立消息队列，避免多个后台结果互相覆盖提示。
3. **本地资料库长期管理。** 已有标签、封面、导入、排序、多选、重命名和 JSON 备份；后续更需要增量扫描、可选文件夹监控、失效路径定位 / 重新关联和便携 M3U 导入导出。当前绝对路径备份跨机器迁移仍需处理路径变化。

### 平台能力仍有边界

- 粘贴歌单链接目前只支持网易云、QQ（`src/library.hpp:101`、`src/business.hpp:3697`）；新平台可发现 / 搜索 / 保存歌单，不等于任意分享链接已支持。
- 歌手 / 专辑能力主要在网易云、QQ、B 站；其他平台仍缺对应目录。应把不支持、需登录、接口失败与空结果分别呈现。
- 译文补全已有多平台原文和网易云匹配路径；酷狗 KRC 内嵌译文尚未消费。LX 的 lyric / pic、AES / RSA、zlib、formData 和完整 Node API 仍不支持，部分脚本不兼容不能简单归为网络坏源。
- Linux 当前主要为 X11 / XWayland，未实现原生 Wayland 后端。此次新增默认播放器 / 拖放逻辑仍需 Linux 编译和不同桌面环境实机确认，不改动已确认正常的输入法。
- 多选常用组合键已实现；后续可补清晰的键盘焦点、快捷键提示及统一批量操作反馈，无需再造一套选择模式。

### 本次音源优化的后续空间

本次已按可用性和加载延迟选源，分平台 / 实际音质记录样本加载和真实流式首段就绪时间，平滑波动，短期连续失败降级，取消不计失败。后台检测不出声。

当前测速只保留在本次运行，固定静默样本仅覆盖 QQ / 网易云，其余平台靠实际点播积累。64 KiB 样本加载延迟不是持续带宽，样本与实际歌曲的 CDN 也可能不同；实际首段数据优先仍不能保证每一首都最快。后续可考虑带脚本内容指纹、网络环境和过期时间的跨启动统计，以及受限的过期数据复测，避免旧结果长期主导排序。

## 7. 建议执行顺序与验证范围

建议按独立提交推进：

1. 后台任务异常 / 生命周期、多实例写入保护。
2. 队列单写入任务与锁外编码。
3. 保持画面不变的歌词可见区遍历、收藏索引。
4. 第三方平台完整歌单分页与缺失状态反馈。
5. 有实测证据后再处理大型歌单共享、JS 桥和编译耗时；格式及闲置代码单独清理。

本轮按用户规则只做必要编译和静态审查，不运行回归。下次明确发布时，重点纳入以下验证：

- 按平台 / 音质优先最快可用源，失败降级、恢复、取消与重新检测；两种 HTTP 后端在忽略 Range、短响应、超时、错误内容时的有界读取。
- 大队列连续编辑、退出排空、多实例和保存失败，确认无丢失修改、无长时间 UI 等锁。
- Windows 默认应用、中文 / 空格路径、拖放、双击转交；Linux 编译、文件 URI、Xdnd、默认应用及桌面环境差异。
- 长歌词及双语歌词保持现有画面与点击行为，用同一歌曲和窗口尺寸比较 CPU；按相同内存口径记录 Windows / Linux 及 FFmpeg 子进程。

本报告是后续任务清单，本次没有实施上述审查建议，也没有运行新的系统交互或内存基准。
